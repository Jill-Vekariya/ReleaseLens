# Scale boundaries and next design

ReleaseLens currently implements a small-corpus, single-process evidence application. This document separates existing mechanisms from proposed work. It does not claim production throughput, distributed consistency, learned retrieval quality, or a tested capacity limit. Use [OPERATIONS.md](OPERATIONS.md) for the local private Docker Desktop deployment and dated `evaluation/` artifacts for measured results.

## What the implementation does

| Area | Implemented behavior | Consequence |
| --- | --- | --- |
| HTTP concurrency | One Uvicorn process; one application-wide `asyncio.Lock` around database-session transactions, including reads and health | Requests wait behind each other; adding workers bypasses this coordination |
| Writes | Expected revision, PostgreSQL row locks for existing documents, uniqueness constraints, and transactional revision/passages/head/change/impact updates | Useful conflict protection, not a distributed ingestion/job protocol |
| SQLite retrieval | Loads authorized current passages into memory; BM25 and exact dot products | Suitable for the demonstration corpus; runtime/memory grow with eligible corpus size |
| PostgreSQL retrieval | SQL project/release/classification/current-head/quarantine/model filters, exact pgvector cosine distance, English FTS with a GIN index and `ts_rank_cd`, then reciprocal rank fusion | Different lexical ranking from SQLite; no HNSW/IVFFlat index or ANN recall claim |
| Candidate depth | Top 20 dense and top 20 lexical candidates; default hybrid requires lexical eligibility | Bounded candidates do not bound the exact underlying search work; synonym-only matches can be omitted |
| Embeddings | Deterministic 384-dimensional feature hashing by default; optional pinned 384-dimensional SentenceTransformer | Default vectors have no learned semantics; quality and CPU latency need separate evaluation |
| Generation | Exact extracts; optional compatible endpoint selects extracts and must pass deterministic validation | Proves authorized quote membership, not relevance, completeness, or general entailment |
| Impact | Historical cited-passage dependencies plus bounded-purpose public synthetic fact counterevidence | Broader natural-language contradictions remain undetected |
| Review | Owner authorization, answer row lock, and unique evidence fingerprint | Idempotent endpoint review for the same observed evidence; no job leases/retry ledger |
| Identity/cache | Static bearer-token map and role/classification ACLs; owner-private answers; no result cache | No identity provider, sessions, tenant model, ACL epoch, or cache invalidation contract |

The process lock covers the HTTP session dependency, not independently started CLI ingestion or verification processes. Run direct ingestion in a maintenance window with application writes paused. Database row locks and uniqueness checks do not make every multi-step read/review coherent across independent writers. Do not increase Uvicorn workers or backend replicas and call the result horizontally scalable.

## Exact impact scope

The original immutable citation remains linked to its answer. A change to a cited logical passage is detected across historical revisions, including an intervening formatting-only revision. Revalidation compares current heads **within the saved answer's release**. A new software release does not by itself invalidate the answer for an old release.

`releaselens/impact.py` also handles a narrow uncited-counterevidence case: ingestion of an introduced or changed **public**, non-quarantined, current **synthetic** fact assertion can queue saved answers in the same project/release whose saved explicit synthetic fact has the same key and a different value, excluding the answer's cited logical origins. Current public counterevidence participates in the review fingerprint and requires manual review. The helper applies no optional cap and can inspect many answers; it is intentionally a small-corpus implementation. It is called in the ingestion transaction, not replayed as an event worker.

Private/internal new evidence is excluded from that wider counterevidence path so a saved answer's pending state, review history, or returned IDs do not disclose the existence of newly introduced restricted evidence. The ingest response exposes only affected answer IDs owned by the caller, even when internal updates queue another owner's answer. Access to an answer and its dependencies is checked before returning a review. This narrow policy is not a general solution to noninterference, tenant isolation, or private contradiction discovery.

General prose contradictions, contradictions without explicit synthetic fact metadata, and arbitrary new sources that challenge an old answer remain unsupported. Changing an upstream prose extract conservatively requests human review. Only explicit synthetic fact replacement supports deterministic `confirmed_stale`; a public synthetic counterexample on a different logical source is a review signal, not a universal truth verdict. Any expanded detector needs human labels, adversarial counterexamples, and a policy for restricted evidence existence.

## Proposed changes before sustained multi-user use

These are design work, not implemented services:

1. **Measure the existing path.** Record corpus size, eligible passages per role/release, query mix, simultaneous clients, database/CPU/memory, queue wait, error rate, and end-to-end p50/p95/p99. Test ingestion during traffic and recovery separately. Compare SQLite and PostgreSQL on their own outputs; do not transfer a local synthetic latency number into a PostgreSQL capacity claim.
2. **Define a corpus snapshot contract.** PostgreSQL's normal transaction isolation plus process serialization is not a distributed immutable read snapshot. Bind retrieval, citation validation, dependency saves, and revalidation to explicit revision heads or an atomic corpus epoch. Decide whether to use repeatable-read transactions or optimistic head checks with retries. Preserve release and encoder scopes through every stage.
3. **Introduce durable jobs deliberately.** An outbox written in the same transaction as a head update can publish impact work. Add stable event IDs, idempotency keys, leases, retry/backoff, dead-letter handling, cancellation, and observable queue age. Preserve old evidence and make review/correction uniqueness explicit. Do not replay the current impact hook: it has no event ledger. Move CPU encoding and large fan-out out of request transactions while keeping atomic publication of ready revisions.
4. **Prove multi-writer behavior before removing the lock.** Separate read and write transactions, handle document creation/update races and lock order, review-versus-ingest races, deadlocks, and retries across real processes. Add process-level integration and failure tests. Only then evaluate replicas and independent worker pools. Bound connection pools and transaction durations to the database's measured capacity.
5. **Plan retrieval indexes from measurements.** Exact search is a useful reference. If needed, add HNSW/IVFFlat with measured recall against that reference, including selective ACL/release filters and sparse authorized corpora. Ensure optional generation never exposes restricted content; oversampling alone is not an authorization policy. Tune lexical indexes/language, partitioning, candidate depth, and reranking against a reviewed held-out set rather than the synthetic demo.
6. **Replace static identity for real users.** Add a trusted identity provider, verified principals, credential lifecycle, and an explicit tenant/resource authorization model. Preserve owner privacy and equivalent missing/unauthorized responses on all object, history, dependency, and change endpoints. Test role revocation and cross-tenant existence leakage. If caching is introduced, scope by principal/tenant, authorization epoch, project/release, revision snapshot, encoder, generator, and retrieval settings.
7. **Add operational controls.** Define backup retention, off-device copies, restore rehearsals, alerts, resource limits, migrations, deployment rollback, and service objectives from actual measurements. Local loopback access is the supported private deployment shape today. Distributed deployment and public access need separate authorization and engineering work.

## Encoder and index migrations

The optional learned encoder accepts a model identifier and an immutable 40-character model revision, rejects non-384-dimensional models, and disables remote model code. A concrete optional is `sentence-transformers/all-MiniLM-L6-v2` at `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`. The identifier is a configuration optional, not evidence of a successful download, encoding run, quality score, or CPU benchmark; consult actual learned-encoder verification artifacts before claiming those outcomes. CPU use needs compatible installed ML dependencies and measured resource requirements; current Compose does not pass these optional settings or install those dependencies.

Search filters by the configured encoder identity, preventing silent comparison of incompatible spaces. It does **not** re-embed an existing corpus when configuration changes. Identical-content ingestion can be a no-op, so rerunning ingestion with a different model is not a migration procedure. For today's optional experiment, use a fresh isolated database and ingest with the same pinned encoder used for queries, keeping the original database and saved evidence intact.

A production migration needs versioned embedding records keyed by immutable passage plus model/revision/preprocessing/dimensions, resumable backfill, completeness/hash checks, side-by-side retrieval evaluation, an atomic active-index switch, and rollback retention. Preserve physical passage IDs and saved citations; do not regenerate evidence identity to migrate an index. Never silently mix feature hashing and learned vectors. Encoder, chunking, lexical parser, reranker, generator, and authorization changes each need separately identifiable versions and reviewed evaluation before promotion.
