**ReleaseLens — A Version-Aware, Evidence-Backed AI Assistant with Documentation Change Intelligence**

# 1. Primary objective

Build ReleaseLens as a portfolio-grade AI system that can:

1. Answer technical questions using documentation from the **correct software release**.
2. Compare documentation and configurations across different versions.
3. Retrieve high-quality evidence using hybrid retrieval, metadata filters, and reranking.
4. Provide verifiable, passage-level citations for meaningful factual claims.
5. Detect contradictory, incomplete, obsolete, and unsupported evidence.
6. Abstain appropriately when sufficient evidence is unavailable.
7. Track which source passages support previously saved answers.
8. Detect meaningful documentation changes.
9. Determine which saved answers may have become unreliable.
10. Revalidate affected answers and explain whether updates are required.
11. Enforce document permissions before retrieval results reach the LLM.
12. Measure accuracy, retrieval performance, security, latency, and operating cost.
13. Provide a clean, interactive interface demonstrating these features.

The signature capability is:

**"The documentation changed. Which previous answers are affected, which are actually incorrect, and what new evidence supports the corrected answers?"**

This should be the project's primary technical differentiator.

# 5. Implement the retrieval system

Build and compare the following configurations.

**Baseline A — Embedding-only RAG**

Implement straightforward vector search and grounded answer generation.

**Baseline B — Hybrid retrieval**

Combine semantic similarity with lexical retrieval. Investigate rank fusion, score normalization, and retrieval depth.

**Baseline C — Hybrid retrieval with reranking**

Rerank retrieved evidence using a justified method. Measure its value against the additional latency and cost.

**Baseline D — Version-aware retrieval**

Add explicit version identification, release filtering, and correct handling of cross-version questions.

**Full ReleaseLens system**

Combine version-aware retrieval with citations, answer dependency tracking, document-change analysis, revalidation, abstention, and access control.

Keep evaluation conditions comparable. Document variations in models, token budgets, and inference configurations.

Include retrieval debugging information for developers without exposing inaccessible or private documents.

Implement tests showing that a question about an older version cannot silently receive newer-release instructions.

# 6. Evidence-backed answers

Every substantive answer must be attributable to supporting evidence.

Provide an answer schema containing:

- User question.
- Selected project and version.
- Generated answer.
- Claim-level evidence references.
- Supporting document passages.
- Canonical source links.
- Evidence conflicts, if present.
- Explicit uncertainty or abstention reason.
- Retrieval and response metadata.
- Saved-answer identifier.

Avoid fabricated citations.

Validate that cited passages actually exist in the authorized document corpus and correspond to the requested version.

Do not use an LLM's assertion that a citation is correct as the sole verification method.

Distinguish between:

- Supported statements.
- Conflicting evidence.
- Missing evidence.
- Evidence from the wrong version.
- Unsupported generated statements.

When a question cannot be answered safely, provide an understandable explanation instead of inventing a response.

# 7. Signature feature — Documentation change intelligence

This must be the most distinctive and carefully engineered part of ReleaseLens.

Implement the following lifecycle:

**Step 1: Save an answer**

Store the answer, versions, generated claims, citations, and supporting passage identifiers.

**Step 2: Update the documentation**

Ingest a new revision, changed release document, or synthetic documentation update.

**Step 3: Detect changes**

Compare source snapshots using normalized content hashes, structural section comparison, and meaningful content differences.

Separate formatting-only changes from potentially meaningful technical changes.

**Step 4: Identify affected answers**

Use the stored answer-to-source dependency graph or database relationships.

Find saved answers referencing changed, removed, or superseded evidence.

**Step 5: Revalidate**

Retrieve the appropriate updated evidence and assess whether the saved answer's substantive claims remain supported.

Do not assume that every document change invalidates an answer.

**Step 6: Classify the result**

Use meaningful states such as:

- Unaffected.
- Revalidation pending.
- Reviewed and still valid.
- Confirmed stale.
- Insufficient evidence.
- Manual review required.

**Step 7: Produce an audit trail**

Show the previous answer, changed evidence, revised assessment, corrected answer when needed, and explanation of the change.

Preserve previous answer versions rather than silently overwriting history.

Evaluate precision and recall of stale-answer detection against independently verified examples.

Avoid letting the same unverified LLM judgment serve as both the detector and its ground truth.

# 8. Access-control and security design

Implement role-based access using synthetic document classifications.

Include public and private documents and at least three simulated user roles.

Enforce authorization in data access and retrieval logic **before evidence reaches the LLM**.

Also enforce authorization when retrieving citations, viewing saved answers, using caches, and revalidating answer dependencies.

Test:

- Unauthorized document retrieval.
- Cross-user leakage.
- Cross-version cache contamination.
- Direct source-ID access.
- Unauthorized citation access.
- Prompt-injection attempts embedded in retrieved documents.
- Attempts to bypass release filtering.
- Incorrectly scoped saved-answer retrieval.
- Unauthorized access to revalidation history.

Use realistic, synthetic adversarial tests.

Review relevant OWASP LLM and RAG security guidance.

Never rely on the LLM alone to enforce permissions.

# 9. Evaluation and research methodology

Create a rigorous evaluation framework—not just a few attractive sample responses.

Target **300–500 manually reviewed evaluation questions** as the final recommended scope.

Include:

- Version-specific questions.
- Cross-version comparisons.
- Conflicting-source questions.
- Unsupported or unanswerable questions.
- Questions with misleading newer documentation.
- Relevant-evidence retrieval questions.
- Documentation-change scenarios.
- Formatting-only change scenarios.
- Role-based permission scenarios.
- Prompt-injection and leakage scenarios.

Start with a smaller reproducible development suite. Expand toward the target as human verification resources permit.

AI can propose candidate questions and evidence annotations, but do not label them "manually verified" until a human actually verifies them.

Maintain a human-review checklist and annotation guidelines.

Establish development, tuning, and held-out test splits. Hold out selected question families or releases to reduce evaluation leakage.

Measure at least:

| Metric | What it demonstrates |
|---|---|
| Version-correct answer rate | Release-specific correctness |
| Retrieval Recall@k | Evidence discovery effectiveness |
| MRR or nDCG | Retrieval ranking quality |
| Citation support rate | Evidence grounding |
| Answer coverage | Willingness to answer |
| Accuracy conditional on answering | Quality versus abstention |
| Abstention precision | Correct handling of uncertainty |
| Stale-answer detection precision | Avoidance of false alarms |
| Stale-answer detection recall | Detection of genuinely outdated answers |
| Unauthorized retrieval rate | Security boundary effectiveness |
| p50/p95 latency | Application responsiveness |
| Cost per query | Inference efficiency |

Report confidence intervals or uncertainty where appropriate.

Include representative successes, failures, and error analysis.

Create an ablation study showing what each major component contributes.

Never invent results. If an experiment has not run, mark its outcome as pending.

Do not retain a query router, reranker, or other advanced feature unless its measured benefits justify the complexity.
